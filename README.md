# Gamertab

Навчальний вебпроєкт для пошуку ігор, персональних рекомендацій і ведення власної ігрової бібліотеки.

[Відкрити Gamertab](https://gamertab-917646089327.us-east1.run.app/)

Грицина Антон Олександрович, ТТП-32.

## Можливості

- Живий каталог ігор для різних платформ із пошуком, фільтром жанру та сторінками результатів.
- Повнотекстовий пошук збережених ігор за назвою, описом, жанрами, темами та режимами.
- Реєстрація з паролем або вхід через Google.
- Власна бібліотека зі статусами Planned, Playing, Completed, On hold і Dropped.
- Особисті оцінки, нотатки та дати проходження.
- Плани Standard і Premium з доступом до статистики за прапорцями можливостей.
- Блоковий Play journal для кожної гри з автозбереженням, перестановкою блоків і експортом Markdown.
- Синхронізація щоденника між браузерами з анімацією перестановок, підсвічуванням змін, локальною чернеткою та вибором версії при конфлікті.
- Локальне підключення ШІ-агента через MCP для роботи з каталогом, бібліотекою й колекціями.
- Чат із Gemini для читання бібліотеки, пошуку збережених ігор та персональних рекомендацій із потоковими відповідями й результатами інструментів.
- Статистика бібліотеки за статусами, жанрами та місяцями завершення ігор.
- Власні колекції ігор із пошуком для додавання нових ігор.
- Завантаження власних обкладинок колекцій у Blob Storage.
- Автоматичне збереження описів ігор з IGDB після відкриття сторінки.
- Доступні оцінки IGDB, вікові рейтинги й орієнтовний час проходження.
- Платформи гри, ціна Steam у USD і доступна оцінка Metacritic для PC.
- Скриншоти з переглядом на весь розмір і відео на сторінці гри.
- Історія новин і оголошень Steam.
- Фонове оновлення новин відстежуваних ігор через чергу завдань.
- Browse із пошуком і популярними іграми та окрема сторінка For you з персональними рекомендаціями.

## Технології

C#, .NET 10, ASP.NET Core MVC, Razor, Bootstrap, PostgreSQL, Entity Framework Core та ASP.NET Core Identity. Для локального середовища використовується Docker Compose у WSL2.

У рішенні є застосунок Gamertab, проєкт Gamertab.Tests та невелика HTTP-функція functions/LibraryExport. У Controllers розташовані обробники сторінок і API, у Models моделі даних, у Data база та міграції, у Services інтеграції й рекомендації, у Views сторінки.

Для пошуку гри під час редагування складу колекції використовуються jQuery 4.0.0 і Select2 4.1.0. Підказки завантажуються із сервера після введення щонайменше трьох символів із затримкою 350 мс. Результати мають сторінки, а вже додані ігри приховуються. Гра імпортується з IGDB після підтвердження додавання. Якщо IGDB недоступний, форма показує повідомлення про недоступність пошуку. Файли бібліотек зберігаються в wwwroot/lib разом із ліцензіями.

Для повнотекстового пошуку використовується Lucene.NET 4.8.0-beta00018. Індекс зберігається в пам'яті, формується з PostgreSQL під час запуску та оновлюється після імпорту чи зміни гри. Окремий сервер для індексу не потрібен. Запит GET `/api/games?q=space%20dwarves` знаходить Deep Rock Galactic за описом. Збіги в назвах мають вищий пріоритет. Пошук враховує слова запиту без урахування регістру та підтримує початок останнього слова. Службові знаки не виконуються як синтаксис запиту. Такий самий пошук доступний в окремому режимі збереженого каталогу з параметром saved=true. Живий каталог отримує результати безпосередньо з IGDB.

Сторінка Statistics відкривається з My library. Графіки побудовано на Chart.js 4.6.1, який зберігається локально разом із ліцензією. Підрахунки виконуються на сервері лише для поточного користувача. Місячний графік охоплює останні 12 календарних місяців і враховує лише завершені ігри з датою завершення. Середня оцінка включає лише виставлені оцінки, зокрема нульові. Біля графіків можна розкрити ті самі дані в текстовому вигляді.

Play journal зберігається в PostgreSQL окремо для акаунта та гри. SignalR 10.0.11 повідомляє відкриті браузери про зміни, після чого вони отримують актуальний документ. Запис через API перевіряє CSRF і номер версії. Стара версія отримує HTTP 409 замість перезапису. За відсутності мережі чернетка зберігається в браузері, а після відновлення зв'язку можна вибрати серверну або власну копію. Попередні локальні щоденники переносяться після відкриття, а при розбіжності пропонується такий самий вибір. Щоденник залишається після видалення гри з бібліотеки й знову доступний після її додавання.

## Пошукові системи та аналітика

Публічні сторінки ігор мають власні описи, canonical URL та Open Graph metadata. Sitemap.xml містить головну сторінку та збережені ігри. Особисті сторінки й результати пошуку позначені noindex. Site:BaseUrl задає основну публічну адресу незалежно від адреси запиту.

Зовнішній аудит PageSpeed Insights для сторінки Portal 2 від 3 листопада 2026 року дав 100/100 у категорії SEO для мобільного пристрою. Це оцінка базових технічних перевірок Lighthouse, а не гарантія позиції в пошуку. [Результат аудиту](https://pagespeed.web.dev/analysis/https-gamertab-917646089327-us-east1-run-app-Games-Details-1/ym9modkp46?form_factor=mobile).

Google Analytics працює лише в Production після добровільної згоди. Analytics preferences у нижній частині сторінки дозволяє змінити вибір. До згоди тег Google не завантажується. Розширений автоматичний збір у вебпотоці вимкнений. Власні події охоплюють перегляди ігор, переходи з рекомендацій, додавання гри до бібліотеки та запуск трейлера. Передаються назва події та ID гри, без пошти, пошукового запиту, нотаток, щоденника чи тексту чату. Адреса сторінки очищена від параметрів, а адреса попередньої сторінки не передається. Google також обробляє стандартні дані браузера та використання. Analytics:MeasurementId містить публічний ID вебпотоку. Для автоматичних перевірок використовується контрольований тег без надсилання даних у Google.

## Експорт бібліотеки

Export Markdown у My library завантажує список ігор, згрупований за статусом, з оцінками, датами та посиланнями. Основний застосунок вибирає лише записи поточного акаунта й передає їх приватній HTTP-функції на Google Functions Framework для .NET 10. Вона формує Markdown без доступу до бази та без збереження вхідних даних. Виклик захищено Google IAM через ідентифікаційний токен runtime-акаунта. LibraryExport:Url задає адресу функції. Локально без адреси використовується той самий форматувач. Експорт щоденника окремої гри працює у браузері незалежно від цього сервісу.

## Звернення до підтримки

Feedback відкриває форму повідомлення про помилку, пропозицію або неточність у даних гри. Застосунок створює ticket у HubSpot CRM через HTTP API. Сторінка звернення показує актуальний статус із CRM. Історія доступна лише автору, а чужий номер звернення повертає 404 до звернення до зовнішнього API. Повідомлення, необов'язкова адреса для відповіді та посилання на вибрану гру передаються в HubSpot після натискання Send feedback. Пошта акаунта й особисті нотатки автоматично не передаються. У PostgreSQL зберігаються власник, тема, категорія, дата й ID ticket. Відповіді CRM виводяться як текст без виконання HTML.

Crm:AccessToken задається локально через HUBSPOT_ACCESS_TOKEN у .env, а в Cloud Run через Secret Manager. Service key має лише crm.objects.tickets.read та crm.objects.tickets.write. За замовчуванням використовуються pipeline 0 і початковий етап 1, їх можна змінити через Crm:PipelineId та Crm:NewStageId. Назви поточних етапів читаються з API CRM. Надсилання обмежено п'ятьма зверненнями за годину на акаунт. Після помилки текст залишається у формі, успішне надсилання не імітується. Автоматичні повторні запити створення не виконуються.

## Активність бібліотеки та способи зв'язку

Activity у My library показує додавання, редагування та видалення записів через вебформи й JSON API. Подія зберігається в PostgreSQL разом зі зміною бібліотеки, без приватних нотаток. Останні події відновлюються після відкриття сторінки. Курсор дозволяє отримувати пропущені зміни без повторення вже показаних подій. За замовчуванням використовується SignalR із повідомленням та читанням змін через API.

Connection details дозволяє перемикатися на звичайний WebSocket, Long polling або Adaptive polling. WebSocket передає документ події через відкрите з'єднання. Long polling чекає до 20 секунд і завершує запит після появи зміни. Adaptive polling збільшує паузу від 1 до 10 секунд за відсутності змін і повертається до короткого інтервалу після нової події. Зміна режиму закриває попереднє з'єднання. Автентифікація, фільтрація за власником і перевірка Origin застосовуються до підключень. Сповіщення між з'єднаннями працюють у межах одного серверного процесу, що відповідає поточному обмеженню Cloud Run одним екземпляром. Перед масштабуванням на кілька екземплярів потрібен спільний канал сповіщень.

Порівняння запускається окремо командою `.\dev.ps1 connectivity-test`. Використовуються локальний Kestrel, SQLite та Edge без зовнішніх API. Для кожного режиму виконуються 12 секунд без змін і вісім оновлень із паузами приблизно в секунду. Час вимірюється від початку запису до появи події у браузері. Початкове підключення входить у вимірювання. Приклад фактичного запуску на цьому комп'ютері наведено нижче.

| Режим | HTTP-запити отримувача | Отримані дані, байти | Середня затримка, мс | Найбільша затримка, мс | CPU .NET, мс | Виділено .NET, КіБ |
|---|---:|---:|---:|---:|---:|---:|
| WebSocket | 0 + 1 WebSocket | 1343 | 19,3 | 79,8 | 3609,4 | 2683 |
| Long polling | 8 | 1318 | 13,3 | 20,7 | 2453,1 | 3569 |
| Adaptive polling | 9 | 1362 | 401,9 | 2048,1 | 1359,4 | 3395 |
| SignalR | 10 + 1 WebSocket | 2123 | 21,1 | 66,6 | 1359,4 | 3844 |

Розмір даних охоплює тіла HTTP-відповідей та вміст отриманих WebSocket-фреймів, включно зі службовими повідомленнями SignalR. HTTP-заголовки, обрамлення WebSocket і TLS не враховані. CPU та виділення пам'яті вимірюються для спільного процесу сервера й вимірювача, без процесу браузера. Короткий прогін і JIT впливають на результат, тому ці числа не визначають універсальний рейтинг методів.

У цьому сценарії Long polling швидко отримує події, але для кожної відповіді потрібен новий HTTP-запит. WebSocket зберігає одне з'єднання. Adaptive polling скорочує частоту перевірок у спокої ціною затримки. SignalR у нашій реалізації надсилає сповіщення, після якого браузер читає події окремим запитом, тому має додаткові повідомлення й дані. Його перевага для основного режиму полягає в готовому керуванні з'єднанням і резервних способах передачі. Повний результат запуску зберігається в connectivity.json у browser-results поруч із тестовою збіркою.

## Запуск

Потрібні .NET 10 SDK, PowerShell і Docker. На цьому комп'ютері Docker працює в Ubuntu-24.04 через WSL2.

```powershell
.\dev.ps1 run
```

Сервіс відкривається за адресою http://localhost:5180. Можна також відкрити Gamertab.slnx у Visual Studio, запустити базу й сховище через dev.ps1 up і вибрати профіль Gamertab.

Команда dev.ps1 run явно запускає локальне середовище Development. Ключі інтеграцій читаються з локального файлу .env у корені проєкту. Використовуються поля IGDB_CLIENT_ID, IGDB_CLIENT_SECRET, GOOGLE_CLIENT_ID та GOOGLE_CLIENT_SECRET. Цей самий файл підтримує Docker Compose, він виключений із Git. Якщо значень у .env немає, використовуються наявні User Secrets. Скрипт передає налаштування дочірньому процесу, а після завершення відновлює попередні змінні середовища. У консолі виводяться шлях до локальних налаштувань і стан Live discovery configured, без ключів.

```powershell
.\dev.ps1 test
.\dev.ps1 down
```

Тести використовують окрему базу SQLite в пам'яті та не змінюють бібліотеку у PostgreSQL. Команда down зупиняє контейнери, зберігаючи дані бази.

## Фонові оновлення новин

NewsUpdateWorker працює у фоні через ASP.NET Core BackgroundService. Раз на 15 хвилин він вибирає ігри, для яких хоча б один користувач увімкнув Follow news, та додає завдання в Azure Storage Queues. До одного пакета гра потрапляє лише один раз. Новий пакет створюється після завершення попереднього. Ігри без Steam App ID пропускаються.

Робітник отримує завдання, перевіряє, чи стежать за грою досі, завантажує оголошення Steam і зберігає нові записи. Повторна доставка не створює копій новин. Повідомлення видаляється після успішної обробки. Невдала обробка повторюється до трьох разів, після чого завдання переходить у чергу gamertab-news-failed. Некоректні повідомлення потрапляють туди одразу. Помилка черги або Steam записується в журнал і не зупиняє сайт.

Локально використовується Azurite 3.37.0 у Docker. Команда dev.ps1 run запускає PostgreSQL і Azurite, вмикає робітника та зберігає локальне підключення до черги в User Secrets. Обліковий запис Azure для цього не потрібен. Порт черги 10001 доступний лише на цьому комп'ютері. Повідомлення зберігаються в Docker volume після зупинки контейнерів.

Перша перевірка ігор з увімкненим Follow news виконується одразу після запуску застосунку. У консолі з'являються повідомлення Queued news updates і Processed news update. Новини доступні на сторінці гри. Під час роботи наступні перевірки відбуваються автоматично.

Налаштування NewsUpdates містяться в appsettings.json. ScanIntervalMinutes задає інтервал планування, PollIntervalSeconds інтервал очікування нових повідомлень, RetryDelaySeconds затримку повторної обробки. Для підключення справжнього Azure Storage потрібно змінити ConnectionStrings:QueueStorage та ввімкнути NewsUpdates:Enabled у конфігурації середовища. Без налаштування черги залишається доступне отримання новин під час відкриття сторінки гри.

## Обкладинки колекцій

Після вибору файлу браузер показує попередній перегляд, назву, розмір і роздільність. File API читає вибраний файл локально та перевіряє розмір, сигнатуру PNG/JPEG і можливість відкрити зображення. Файл надсилається лише після Save collection. Тимчасові object URL звільняються після зміни вибору або виходу зі сторінки. Серверні перевірки залишаються обов'язковими.

У формі створення або редагування колекції є один блок обкладинки. Можна вибрати HTTPS-посилання, файл PNG/JPEG до 2 МБ або відсутність обкладинки. Назва, опис і вибрана обкладинка зберігаються однією кнопкою. Для наявного файлу порожнє поле завантаження означає збереження поточного зображення. Перехід на посилання або вибір No cover видаляє попередній завантажений файл.

Сервер перевіряє розмір і сигнатуру файлу та генерує власне ім'я. JSON API також підтримує окремі операції з обкладинкою.

Зображення зберігаються у приватному сховищі. Локально використовується Azure Blob Storage через Azurite, а на публічному сайті Google Cloud Storage. Застосунок перевіряє власника колекції перед читанням і зміною файлу. Ключі сховища не передаються браузеру. Заміна обкладинки та видалення колекції також видаляють попередній файл. Помилки очищення сховища записуються в журнал.

Локально Blob Storage працює в тому самому Azurite, що й черги. Команди dev.ps1 up і run запускають обидва сервіси. Порт Blob Storage 10000 доступний лише на цьому комп'ютері. Дані зберігаються в Docker volume. За замовчуванням використовується ConnectionStrings:QueueStorage. Окреме підключення можна задати через ConnectionStrings:BlobStorage, а назву контейнера через BlobStorage:ContainerName. Без підключення сховища залишається доступне зовнішнє посилання на обкладинку.

Для хмарного сховища задається BlobStorage:GoogleBucket. Застосунок отримує доступ через runtime-акаунт Cloud Run без JSON-ключів. Акаунт має роль Storage Object User лише для цього bucket. Uniform bucket-level access і Public access prevention забороняють публічне читання файлів. Зображення повертає захищений маршрут Gamertab після перевірки власника колекції.

## Плани та ігровий щоденник


За замовчуванням акаунт має план Standard. Statistics доступна Premium за прапорцем LibraryStatistics. Плани зберігаються в таблиці UserPlans, а прапорці налаштовуються в секції Features у appsettings.json. Доступ перевіряється на сервері при кожному відкритті сторінки. Standard отримує HTTP 403 із поясненням, без даних статистики. Зміна плану діє без повторного входу.

В Account settings є Upgrade to Premium та Switch to Standard. Це демо без оплати, яке змінює лише план поточного акаунта. Воно доступне локально в Development, а в інших середовищах вмикається окремим прапорцем Features:AllowDemoPlanChanges. На навчальному публічному сайті цей прапорець увімкнений. За замовчуванням для інших розгортань він вимкнений.

Journal відкривається з My library або редагування запису гри. Він підтримує блоки тексту, заголовків і списків, попередній перегляд, Markdown source та Export Markdown. Порядок змінюється перетягуванням або кнопками зі стрілками. Перестановка анімується, якщо користувач не ввімкнув зменшення анімацій у браузері чи системі.

Зміни надходять до інших відкритих щоденників того самого акаунта й гри без перезавантаження. Додані та відредаговані блоки короткочасно підсвічуються, переставлені блоки плавно переміщуються, а над документом з'являється повідомлення про зміну. При зменшенні анімацій залишається підсвічування. Постійні ідентифікатори розрізняють навіть блоки з однаковим текстом і зберігають фокус та позицію курсора при оновленні. Старі документи отримують ідентифікатори автоматично без зміни тексту.

Документ автоматично зберігається на сервері, а браузер тримає локальну копію та чернетку поточної вкладки. Статус Synced to your account означає, що зміни вже прийняті сервером. Під час конфлікту Load server copy завантажує серверну версію, а Save my draft instead зберігає власну поверх останньої відомої версії. Якщо інша сесія встигне змінити її ще раз, сайт знову попросить вибрати. Перед вибором можна експортувати Markdown. Пошкоджена локальна копія автоматично не перезаписується.

## Доступ до IGDB

IGDB використовує доступ через зареєстрований Twitch-застосунок. Для запуску через dev.ps1 ключі можна задати в локальному .env як IGDB_CLIENT_ID та IGDB_CLIENT_SECRET. Скрипт також переносить їх у .NET User Secrets для запуску через Visual Studio. Секретні налаштування виключені з Git.

У Visual Studio можна вибрати Manage User Secrets для проєкту Gamertab. У VS Code можна відкрити файл `%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json`, де UserSecretsId вказаний у Gamertab.csproj. Потрібні поля Igdb:ClientId та Igdb:ClientSecret. Паролі й ключі в Git не додаються.

Для новин конкретної гри використовується Steam News API. Імпорт бібліотеки Steam буде окремою можливістю. Бібліотека облікового запису відрізняється від переліку ігор, установлених на певному ПК.

Пошук на головній сторінці й у формі додавання до колекції звертається до IGDB та не обмежений іграми в локальній базі. Пошук охоплює різні платформи. Без пошукового запиту доступні популярні ігри за кількістю оцінок. Модифікації, комплекти та дублікати спеціальних видань відфільтровуються. Відкрити опис гри можна без акаунта. До локальної бази потрапляють лише відкриті або додані до колекції ігри. Якщо точного збігу на сторінці немає, інші результати IGDB показуються з поясненням. Якщо служба недоступна чи не налаштована, показується помилка з кнопкою повтору, без підміни результатів локальними іграми. За бажанням можна окремо перейти до пошуку збережених ігор через Search saved games або параметр saved=true.

Персональні рекомендації розміщені на окремій сторінці For you. Їх основою є високо оцінені, поточні та пройдені ігри. Низько оцінені й покинуті ігри не використовуються як уподобання. Кандидати надходять із переліків схожих ігор IGDB та окремого пошуку за жанрами, темами й перспективою гри. Збіг лише за режимом Single player недостатній. Загальні позначки Adventure, Indie та Action мають меншу вагу. Уже додані до бібліотеки ігри виключаються, а кожна рекомендація має пояснення. Перспектива використовується під час живого підбору й окремо не зберігається в базі.

## Вхід через Google

У Google Cloud Console потрібно створити проєкт, налаштувати Google Auth Platform і додати OAuth-клієнт типу Web application. Для локального запуску його Authorized redirect URI має бути `http://localhost:5180/signin-google`.

У .NET User Secrets потрібні поля `Authentication:Google:ClientId` та `Authentication:Google:ClientSecret`. Після їх додавання застосунок потрібно перезапустити. Для запуску всього сервісу через Docker Compose ці значення передаються через змінні `GOOGLE_CLIENT_ID` та `GOOGLE_CLIENT_SECRET`.

Новий користувач отримує акаунт після підтвердженого входу в Google. Для наявного акаунта з паролем потрібно спочатку ввійти звичайним способом, відкрити Account і натиснути Connect Google. Збіг адреси пошти не підключає Google автоматично. Після підключення обидва способи входу відкривають ту саму бібліотеку.

У режимі Testing користувачів для перевірки потрібно додавати в Audience у Google Auth Platform. Якщо клієнт Google не налаштований, залишається доступний вхід із паролем. Gamertab запитує лише основні дані профілю та адресу пошти, без доступу до Gmail або Google Drive.

## Дані про ігри

Сторінка гри містить опис, рейтинги, медіа, ціну, час проходження та новини в одному місці. Компактна панель переходів залишається зверху під час прокручування. Feedback відкриває сторінку звернень у GitHub.

Скриншоти й ідентифікатори відео завантажуються з IGDB окремим запитом із кешуванням на 10 хвилин. Показується до шести різних скриншотів. У переглядачі працюють кнопки перемикання, стрілки клавіатури й Escape. Для відео спочатку вибирається трейлер, якщо він доступний. Плеєр YouTube завантажується лише після натискання Play, також є пряме посилання на відео. Відсутність медіа не створює порожніх блоків, а помилка джерела не заважає переглядати іншу інформацію про гру. База даних і файли відео для цієї можливості не збільшуються.

Біля зовнішніх даних зазначається джерело. Оцінка критиків IGDB не є оцінкою Metacritic. Оцінка Metacritic для PC показується окремо лише тоді, коли її надає картка Steam. За наявності додається пряме посилання на Metacritic. Для ігор без такої оцінки блок прихований. Це не гарантує покриття всіх ігор, оцінених на самому Metacritic.

Ціна, знижка та безкоштовний доступ беруться з публічного endpoint Steam Store appdetails для магазину США. Відповідь кешується на 10 хвилин. Показуються лише ціни, які джерело позначило як USD. Біля ціни є час отримання та уточнення про регіон. Відсутня ціна не замінюється нулем. Цей endpoint відрізняється від документованого Steam Web API й може змінитися. Його недоступність не блокує опис гри. Для ігор без зв'язку зі Steam ціна не вигадується. Платформи надходять з IGDB незалежно від наявності в Steam.

IGDB може надавати час до титрів, час із частиною додаткових завдань і час на проходження на 100%. Наявність цих значень залежить від гри. Повне проходження не означає автоматичне включення всіх DLC. Відсутні значення не замінюються нулем.

Невеликий початковий каталог дозволяє відкрити сервіс до підключення API. Його описи підготовлено для початку роботи, а неперевірені оцінки та час проходження залишено порожніми.

## Розгортання в Google Cloud

Публічний сервіс працює в Cloud Run, а PostgreSQL у Neon Free. Застосунок збирається з Dockerfile та слухає порт 8080. Мінімальна кількість екземплярів дорівнює нулю, максимальна одному. Після простою перший запит може виконуватися довше. Дані хмарної версії зберігаються окремо від локальної бази.

Workflow `.github/workflows/deploy.yml` запускає тести, збирає контейнер, передає його в Artifact Registry і розгортає main у Cloud Run. Після оновлення перевіряється `/health`. Pull request виконує лише збірку й тести. Для автентифікації використовується Workload Identity Federation із доступом лише для main у цьому репозиторії. Постійний JSON-ключ сервісного акаунта не потрібен. Правила infra/artifact-cleanup.json видаляють образи, старші за добу, зі збереженням трьох останніх версій.

Змінні репозиторію GCP_PROJECT_ID, GCP_REGION, GCP_WORKLOAD_IDENTITY_PROVIDER, GCP_DEPLOY_ACCOUNT, GCP_RUNTIME_ACCOUNT та GCP_COVER_BUCKET задають розміщення й облікові записи. Обліковий запис деплою має доступ до оновлення одного сервісу, запису в один репозиторій контейнерів і використання runtime-акаунта.

Підключення PostgreSQL, секрети Google та IGDB, ключ Gemini й сертифікат захисту сесій передаються через Secret Manager. Runtime-акаунт може читати лише ці секрети. Ключі ASP.NET Core Data Protection зберігаються в PostgreSQL у зашифрованому вигляді, тому входи й CSRF-токени переживають заміну контейнера. Підключення до Neon перевіряє TLS-сертифікат.

У Cloud Run налаштовано ASPNETCORE_FORWARDEDHEADERS_ENABLED=true для HTTPS за проксі Google. Для входу через Google до OAuth-клієнта потрібно додати публічний HTTPS-домен зі шляхом `/signin-google`.

Хмарне розгортання використовує Google Cloud Storage для файлів обкладинок. Новини оновлюються під час відкриття сторінки гри. Фонова черга новин поки працює локально через Azurite і не підключена до Cloud Run.

Google Cloud використовує Free Trial без переходу на Paid. Після вичерпання кредитів або завершення trial ресурси можуть зупинитися. Neon використовує Free plan. Перед зміною тарифів чи лімітів потрібно перевіряти актуальні умови провайдерів. Попередній шаблон Azure у папці infra не використовується цим workflow.

3. Покращити рекомендації з урахуванням реакцій користувача.
4. Розширити фільтри каталогу.
5. Додати імпорт і експорт бібліотеки.
6. Підключити фонові оновлення новин до хмарного середовища.

Мета проєкту полягає в послідовному вивченні веброзробки на робочому сервісі. Нові можливості додаються після перевірки попередніх.

## Чат із Gemini

Assistant доступний після входу. Сервер звертається до Gemini API, передає текст поступово через Server-Sent Events і показує виконання інструментів та отримані ігри. Агент читає бібліотеку поточного користувача, шукає в збереженому каталозі й отримує рекомендації. Для пошуку нової гри в IGDB використовується Browse. Агент не змінює бібліотеку. Він не отримує пошту, приватні нотатки чи Play journal.

Для локального запуску у файлі `.env` потрібно додати `GEMINI_API_KEY=...` і перезапустити `.\dev.ps1 run`. Ключ створюється в [Google AI Studio](https://aistudio.google.com/api-keys) для проєкту Free tier. Платний білінг для цього не підключається. На безкоштовному тарифі діють квоти, а Google може використовувати передані запити й відповіді для покращення продуктів.

Типова модель `gemini-3.5-flash-lite` з мінімальним рівнем роздумів для швидких відповідей та виклику інструментів. Її можна змінити серверним налаштуванням `Gemini:Model` або змінною середовища `Gemini__Model` на модель із підтримкою `thinkingLevel: minimal`. Модель та доступність безкоштовної квоти потрібно звіряти в AI Studio. При перевантаженні або очікуванні заголовків відповіді понад 25 секунд сервер повторює запит один раз. API-ключ залишається на сервері й не потрапляє в JavaScript чи Git.

Stop скасовує поточний запит. New conversation очищує діалог. Історія зберігається лише в пам'яті відкритої сторінки, до моделі передаються останні десять повідомлень. Є обмеження шість запитів за хвилину для одного акаунта, п'ять раундів звернень до моделі й 90 секунд на відповідь. Помилки та вичерпання квоти показуються в чаті. При HTTP 500, 502, 503 або 504 до початку потоку сервер повторює запит один раз; квота HTTP 429 не спричиняє повтору. Часткова відповідь після зупинки не додається до історії. Під час генерації підтримуються заголовки, списки, виділення, код і посилання на сторінки ігор. HTML від моделі не виконується.

## Підключення агента через MCP

Codex CLI можна відкрити з уже підключеним Gamertab. Команда знаходить CLI у PATH або серед файлів встановленого застосунку Codex і не змінює глобальну конфігурацію. Вкажи адресу наявного акаунта саме в локальному Gamertab.

```powershell
.\dev.ps1 mcp-client -AccountEmail you@example.com
```

Для перевірки параметрів без запуску чату додай `-Check`. У відкритому клієнті команда `/mcp` показує підключені MCP-сервери.

У тому самому C# проєкті є окремий режим локального MCP-сервера на офіційному ModelContextProtocol SDK 2.3.0. Він працює через stdin/stdout і не відкриває публічний порт. Потрібні запущена база, застосовані міграції та вже створений акаунт Gamertab.

Команда запуску для MCP-клієнта виглядає так. Замість адреси з прикладу потрібно вказати пошту свого акаунта.

```powershell
.\dev.ps1 mcp -AccountEmail you@example.com
```

Цю команду запускає MCP-клієнт. Після ручного запуску вона чекатиме протокольні повідомлення, а не звичайні команди в консолі. Налаштування PostgreSQL беруться з локального `.env`, а при явному налаштуванні сервера можна передати `ConnectionStrings__Gamertab` і `Mcp__AccountEmail` через середовище.

Приклад конфігурації для Codex. Шлях до проєкту та пошту потрібно підставити власні.

```toml
[mcp_servers.gamertab]
command = "powershell.exe"
args = ["-NoProfile", "-File", 'Q:\vs\Gamertab\dev.ps1', "mcp", "-AccountEmail", "you@example.com"]
startup_timeout_sec = 60
```

Доступні інструменти `search_games`, `get_library`, `list_collections` і `add_to_library`. Пошук використовує збережений каталог Gamertab. Щоб працювати з новою грою, спершу можна відкрити її сторінку на сайті й імпортувати з IGDB. Додавання через агента створює запис Planned, а вже наявний прогрес, оцінки та нотатки залишає без змін.

Сервер прив'язується до одного акаунта під час запуску, інструменти не приймають ідентифікатор іншого користувача. Це локальний доступ від імені власника комп'ютера, тому конфігурацію слід давати довіреному MCP-клієнту. Публічної HTTP-авторизації цей режим не реалізує.

## Перевірки

Браузерні тести написані на C# із Playwright. Вони запускають окремий Kestrel на випадковому порту, використовують тимчасову SQLite у пам'яті та контрольовані відповіді IGDB і Steam. Основна база й особисті акаунти не змінюються. Потрібен встановлений Microsoft Edge. Можна вибрати встановлений Chrome через змінну GAMERTAB_TEST_BROWSER зі значенням chrome. Завантажувати окремий браузер не потрібно, сам браузер працює у фоновому режимі.

```powershell
.\dev.ps1 browser-test
```

Браузерні сценарії перевіряють реєстрацію та вхід, пошук і збереження прогресу, роботу Select2 і колекцій, ізоляцію акаунтів, галерею й відкладене завантаження трейлера, графіки та відображення статистики на вузькому екрані. Зовнішні картинки й відео в тестах замінено контрольованими відповідями, тому їх доступність не впливає на результат. Додаткові сценарії перевіряють доступ до Premium, локальний перегляд файлу без завантаження, перестановку блоків, експорт та відновлення щоденника після повного перезапуску браузера. Для цього створюється окремий тимчасовий браузерний профіль. Синхронізація перевіряється у двох незалежних браузерних контекстах одного акаунта, включно з перенесенням старих локальних нотаток, змінами без перезавантаження, роботою без мережі й конфліктом версій. Окремо перевіряються рух і підсвічування блоків після дій в іншому браузері, збереження фокуса й курсора, блоки з однаковим текстом та перемикання налаштування зменшення анімацій. Справжній вхід у Google не автоматизується цими сценаріями.

Команда також вимірює покриття рядків і гілок .NET через Coverlet, показує відсотки та зберігає coverage.cobertura.xml у `.local\browser-tests`. Це покриття серверного коду браузерними сценаріями, включно з міграціями, а не відсоток перевірених можливостей або покриття JavaScript. Звичайні перевірки без браузера запускаються через `.\dev.ps1 test`. Обидві команди використовують окрему папку збірки й можуть працювати паралельно з відкритим сайтом.

Перевіряємо доступ до власних записів, правильність дат і оцінок, повторне додавання ігор, пагінацію та захист операцій зміни даних. Звичайні автоматичні тести мають працювати без ключів зовнішніх служб. Живі інтеграції перевіряються окремо.

У Gamertab.Tests є автоматичні перевірки основних можливостей. Перевірки Google проходять через справжній обробник OAuth із контрольованими відповідями зовнішньої служби. Вони перевіряють створення та підключення акаунтів, відмову від входу, захист state і cookie, небезпечні адреси повернення та збереження бібліотеки. Пошук перевіряється з контрольованими відповідями IGDB. Для вибору гри в колекцію перевіряються мінімальна довжина запиту, сторінки, імпорт після підтвердження, дублікати, робота без IGDB та доступ лише власника. Окремі перевірки кешу підтверджують повторне використання відповідей, розділення пошуку та сторінок і очищення після зміни гри. Повнотекстовий пошук перевіряється за описами й темами, для початку слова, ранжування, сторінок, великих зміщень та оновлення індексу після імпорту. Реальний вхід через Google та живі дані перевіряються окремо.

Для черг є ще 4 інтеграційні тести з реальним Azurite та окремими тимчасовими чергами. Вони перевіряють фонову обробку без відкриття сторінок, повторну доставку, вимкнення Follow news, повторні спроби й чергу помилок. Відповіді Steam у цих тестах контрольовані. Запуск виконується окремо.

```powershell
.\dev.ps1 queue-test
```

Без цієї команди тести черг пропускаються, щоб звичайні перевірки могли працювати без Docker. Тестові черги видаляються після завершення перевірок.

Окрема перевірка обкладинок використовує справжній локальний Blob Storage. Вона перевіряє завантаження, заміну й видалення файлів, обмеження доступу та відхилення неправильних і завеликих файлів. Також перевіряється збереження бібліотеки після видалення колекції.

```powershell
.\dev.ps1 blob-test
```

Для цих перевірок створюються окремі тимчасові контейнери, які видаляються після завершення. Без цієї команди тести Blob Storage пропускаються. Власні колекції користувача не змінюються.

У папці api-tests міститься колекція Gamertab.postman_collection.json із 40 запитами та 65 перевірками. Вона перевіряє каталог, реєстрацію, вхід і вихід, операції з бібліотекою та колекціями, дублікати, неправильні дати й оцінки, захист CSRF і доступ без входу. Окремі запити перевіряють повнотекстовий пошук за описом і тематикою.

Для запуску потрібен [Postman CLI](https://learning.postman.com/docs/postman-cli/postman-cli-installation/). Скрипт знаходить його через PATH або за локальним шляхом `.local\tools\postman\postman-cli.exe`. На цьому комп'ютері використовується локальний варіант на диску Q.

```powershell
.\dev.ps1 api-test
```

Команда створює тимчасову базу PostgreSQL, застосовує міграції, запускає окремий екземпляр Gamertab і виконує колекцію без ключів зовнішніх служб. Після завершення вона зупиняє тестовий сервер і видаляє тимчасову базу разом із тестовим акаунтом. Основна база залишається без змін. Результат зберігається у файлі results.txt в окремій папці `.local\postman`. Вхід у Postman для локального запуску не потрібен. Повідомлення CLI про авторизацію стосуються публікації результатів у хмарі.

Колекцію можна також імпортувати в Postman і запустити вручну. Змінна baseUrl за замовчуванням містить `http://localhost:5180`. Такий запуск створює тестовий акаунт у вибраній базі й видаляє створені ним записи бібліотеки та колекцій.

## Кешування API

Відповіді GET `/api/games` і `/api/games/{id}` для відвідувачів без входу зберігаються в пам'яті сервера на 60 секунд через ASP.NET Core Output Cache. Пошуковий запит, розмір сторінки, її зміщення та адреса гри враховуються окремо. Після імпорту або оновлення гри кеш каталогу очищається.

Запити користувачів після входу обходять спільний кеш. Особисті бібліотеки, колекції та дані сесії в нього не потрапляють. Відповіді з помилками також не зберігаються. Кеш зовнішніх запитів IGDB і Steam працює окремо.
